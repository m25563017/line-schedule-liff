# ADR-0001：以 LINE LIFF 網頁作為產品形態

> **關於本文件**：此決策在專案初期就已做出，本文件為事後補寫。「考慮過的選項」中，作者當時未正式比較其他方案，下列選項為事後補充的評估，用來說明這個決策的取捨。

## 背景與問題陳述

「揪吉」要解決的是多人喬聚會時間的問題。使用者之間的溝通本來就發生在 LINE 上。如果產品另外要求使用者下載 App，或切換到其他網站，推廣的阻力會很高，也容易讓活動連結散落在不同的地方。

專案作者參考了 Lightsplit 這類在 LINE 內使用的服務，認為把產品放進 LINE 是最符合使用情境的形態。

需要決定的是：產品要以什麼形態提供給使用者？

## 決策驅動因素

- 使用者不需要安裝任何東西，點連結就能用
- 使用者身分可以直接取得，不必另外建立註冊登入流程
- 活動連結與提醒能直接分享到 LINE 聊天室，不需要離開對話
- 個人專案，開發與營運成本要低

## 考慮過的選項

- **A. LINE LIFF 網頁應用（Vue SPA 嵌入 LINE）**
- **B. 原生 App（iOS 與 Android）**
- **C. 獨立網站（自建帳號系統或第三方登入）**
- **D. 純 LINE 機器人（只用 Messaging API，在聊天室內以訊息互動）**

## 決策結果

選擇 **A. LINE LIFF 網頁應用**，因為它同時滿足「免安裝」「身分現成」「可分享回聊天室」三個最重要的驅動因素，且前端技術就是一般網頁，個人開發成本最低。

### 後果

**好處**

- 使用者在 LINE 內點開即用，無需安裝
- 以 `liff.getProfile()` 取得 `userId`、暱稱、頭像，省去註冊登入系統
- 以 `liff.shareTargetPicker` 把邀請與定案卡片分享到任何聊天室，機器人不必加入群組
- 就是一般網頁，沿用 Vue 生態系，部署在 Firebase Hosting 即可

**代價與限制**

- 產品綁定 LINE 平台，使用者必須有 LINE
- LIFF 的 Endpoint URL 必須是 HTTPS，且 LIFF ID 與 LINE Developers Console 的設定須和程式一致
- 在 LINE 以外的瀏覽器開啟時無法取得 LIFF 身分，因此另外做了訪客預覽模式
- 活動提醒與定案通知由主揪手動分享，並非系統自動推播（避免付費的 Push Message）
- 使用者身分目前由前端從 LIFF 取得，後端驗證與權限控管列為後續改進項目

### 驗證方式

於 LINE 內開啟 LIFF 網址，確認可取得使用者資料，並可透過分享目標選擇器把訊息送到聊天室。

## 各選項的優缺點

### A. LINE LIFF 網頁應用（採用）

- 好：免安裝、身分現成、可分享回 LINE、開發成本低
- 好：介面可自由設計（月曆、統計、彈窗），不受訊息格式限制
- 壞：綁定 LINE；需處理 LIFF 的設定與瀏覽器環境差異

### B. 原生 App

- 好：可使用完整的裝置功能與推播
- 壞：需要使用者下載安裝，推廣阻力最高
- 壞：iOS 與 Android 要各自開發與上架審查，個人專案成本過高
- 壞：需要自己做帳號系統

### C. 獨立網站

- 好：不綁定特定平台，任何瀏覽器都能開
- 壞：需要自己做登入與帳號，或接第三方登入，使用者要多一道註冊手續
- 壞：與 LINE 的對話脫節，連結需手動貼到聊天室，無法直接取得 LINE 身分

### D. 純 LINE 機器人

- 好：完全在聊天室內，使用者零學習成本
- 壞：訊息與按鈕的互動形式有限，難以呈現「多個月份的月曆勾選」與「每日有空名單」這類視覺化操作
- 壞：機器人若要在群組內運作，需要被加入群組；本專案刻意避免這個要求
